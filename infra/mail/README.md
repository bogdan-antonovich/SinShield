# SinShield mail infrastructure

This deployment provides a lightweight, single-server mail stack:

- Stalwart for SMTP, submission, IMAP, DKIM, filtering, and mailbox storage.
- Roundcube for webmail at `https://mail.sinshield.app/webmail/`.
- Stalwart administration at `https://mail.sinshield.app/admin`.
- Host Nginx and Certbot for public HTTPS.

Mail state is deliberately kept outside Git under `/srv/stalwart`. Deployments must never replace that directory.

## Architecture and ports

| Endpoint | Binding | Purpose |
| --- | --- | --- |
| TCP 25 | `72.60.118.148` | Server-to-server SMTP |
| TCP 465 | `72.60.118.148` | Implicit-TLS submission |
| TCP 587 | `72.60.118.148` | STARTTLS submission |
| TCP 993 | `72.60.118.148` | IMAPS |
| TCP 8080 | `127.0.0.1` | Stalwart HTTP behind Nginx |
| TCP 9002 | `127.0.0.1` | Roundcube behind Nginx |

The Compose network gives Stalwart the internal alias `mail.sinshield.app`, allowing Roundcube to validate Stalwart's certificate without routing through the public interface.

## Required public DNS

Before deployment:

```text
mail.sinshield.app.  A    72.60.118.148
72.60.118.148        PTR  mail.sinshield.app.
```

Do not add the MX record until Stalwart is configured, its TLS certificate is installed, and inbound delivery tests pass. The mail hostname must not have an `AAAA` record while this deployment is configured for IPv4 only.

## GitHub configuration

The workflow reuses these existing secrets:

- `VPS_HOST`
- `VPS_USER`
- `VPS_SSH_KEY`

Create a GitHub environment named `production-mail` and add required reviewers. Optionally define `MAIL_IPV4`; it defaults to `72.60.118.148`.

## First deployment

1. Run the **Mail Infrastructure** workflow with `operation=upload-only`. This copies the deployment files to `~/sinshield-mail` without starting containers.
2. SSH to the VPS and run:

   ```bash
   sudo ~/sinshield-mail/scripts/bootstrap-host.sh
   ```

   The script creates persistent directories, installs the Nginx site, obtains the `mail.sinshield.app` certificate through Certbot, generates Roundcube's local encryption key, and installs the renewal hook.

   It also adds the deployment user to the local group with GID 2000 so deployments can create consistent backups of Stalwart-owned files. This takes effect on the next SSH login, which is why the deploy operation must be a separate workflow run.

3. Run the workflow again with `operation=deploy`.
4. Retrieve the one-time Stalwart bootstrap credentials without sharing them:

   ```bash
   docker logs stalwart 2>&1 | grep -A8 'bootstrap mode'
   ```

5. Open `https://mail.sinshield.app/admin` and complete the wizard:

   ```text
   Server hostname:             mail.sinshield.app
   Default email domain:        sinshield.app
   Automatically obtain TLS:    Off
   Generate email signing keys: On
   Storage:                     Default RocksDB stores
   Directory:                   Internal Directory
   DNS management:              Manual
   ```

   Save the permanent administrator credentials displayed on the final screen.

6. Restart the container:

   ```bash
   docker restart stalwart
   ```

## Configure Stalwart TLS

In the Stalwart admin UI, create a manual certificate using file references:

```text
Certificate: /certs/fullchain.pem
Private key: /certs/privkey.pem
```

Select it as the default certificate under the network service settings. The Certbot deploy hook copies renewed certificates to `/srv/stalwart/certs` and restarts Stalwart.

Do not expose port 8080 publicly after bootstrap. It remains bound to loopback and is available only through Nginx.

## Create the support mailbox and finish DNS

After TLS is working:

1. Create the individual account `support@sinshield.app` in Stalwart.
2. Copy the exact SPF, DKIM, DMARC, MX, autoconfig, and MTA-STS records shown by Stalwart into Hostinger DNS.
3. Start DMARC with `p=none`; move to `quarantine` and then `reject` after reviewing reports.
4. Test inbound and outbound delivery before publishing the address.

Avoid inventing DKIM selectors or copying example keys: use the values generated by this Stalwart installation.

## Deployments and rollback

The workflow deploys only when manually dispatched. It does not run with the web application deployment.

Before replacing a running container, `deploy.sh` stops the mail services briefly and writes a consistent archive under `/srv/stalwart/backups`. Mail senders retry temporary delivery failures, but schedule upgrades deliberately.

To roll back, run the workflow with the previous full image reference or digest, for example:

```text
stalwartlabs/stalwart@sha256:<previous-digest>
```

Do not restore an older data backup merely to downgrade an image unless the Stalwart release notes explicitly require it.

## Manual operations

Run a backup:

```bash
~/sinshield-mail/scripts/backup.sh
```

Check service health:

```bash
~/sinshield-mail/scripts/health-check.sh
```

Inspect logs:

```bash
docker logs --tail 200 stalwart
docker logs --tail 200 sinshield-roundcube
```

Backups contain mailbox content and secrets. Keep `/srv/stalwart/backups` mode `0700`, copy archives to a separate protected system, and test restoration periodically.
